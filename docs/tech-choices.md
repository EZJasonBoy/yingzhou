# 技术选型对比

> 2026-11-14 重新评估。对照对象主要是 [MisaTV](https://github.com/yagami-hue/MisaTV)（Win-box 作者的 Flutter 重写，GPL-3.0，1.0.0 发布于 2026-11-11），读的是它的源码而不是介绍；其余方案按各自的公开特性比较。本文里关于本项目的数字都是当天在这台机器上实测的。

## 结论

1. **不换技术栈**：继续「Kotlin 引擎 + Flutter 客户端 + HTTP 协议」。
2. 真正决定成败的不是界面框架，而是**协议逻辑放在哪**。MisaTV 把全部逻辑写在 Dart 里，JVM 只是被调用的辅助进程；本项目把全部逻辑放在一个常驻的 Kotlin 引擎里，Flutter 只做界面。两条路各有代价，见第 2 节。
3. **MisaTV 现在比本项目成熟得多**：功能多一个量级，并且在真实的 jar（含加固壳）上反复验证过。只要一个今天就好用的 Windows 客户端，它已经是了。本项目的价值在它没有的东西：macOS、可独立部署的引擎（NAS / 局域网 / iOS 客户端）、与安卓 TVBox 同构的 jar 运行方式。
4. 从 MisaTV 的实现里学到的两件事当天就改了：关闭 Impeller、给引擎 JVM 限定堆。空载提交内存从 1064 MB 降到 335 MB（第 4 节）。

## 1. MisaTV 实际是怎么做的

| 方面 | 实现 |
|---|---|
| 规模 | Dart 约 7.7 万行（services 3.4 万、ui 3.3 万），67 个测试文件约 9 千行。最大的文件：设置页 7707 行、播放页 4097 行、`jar_spider.dart` 4096 行、`app_state.dart` 3029 行 |
| 平台 | 仓库里只有 `windows/`、`android/`、`web/`，没有 macOS / Linux 工程。README 把 Windows 列为主目标；JVM 运行时的安装代码写明"目前仅支持 Windows"，所以 **Android 版跑不了 jar 蜘蛛** |
| 状态与存储 | 一个 `AppState`（`ChangeNotifier`）管全部状态；持久化只有 `shared_preferences`（历史、收藏、网盘 Cookie 都在里面），没有数据库 |
| 订阅 / 采集站 / 直播 / 去广告 | 全部用 Dart 重写（配置解析、MovieParser、直播解析、`m3u8_purify` 逐函数移植自 TVBox） |
| JS 蜘蛛 | `flutter_js`（QuickJS）跑在独立 isolate；蜘蛛要的同步 `req()` 靠**每次请求起一个 `curl.exe` 子进程**实现 |
| jar 蜘蛛 | 首次使用时**下载** JRE 17 + dex2jar + okhttp 等（约 85 MB，多个镜像测速）；Dart 用 `Process.start` 拉起 JVM，反射调用预编译的 `stubs.jar` 里的运行器，stdin / stdout 走一行一个 JSON 的协议。三种进程形态：一次性调用、常驻池（每个 jar 最多 3 个 JVM，45 秒空闲回收）、播放期间保活的 `--hold` 进程 |
| 加固 jar | 首次用 unidbg（ARM 模拟器，另下约 39 MB）把壳里的真实实现解出来缓存，之后用纯 Java 的影子类（shell-shim）加载；针对具体壳家族有专门的补丁 jar |
| Python 蜘蛛 | 首次使用时下载嵌入式 CPython 3.11，`runner.py` 做桥 |
| 嗅探 | `flutter_inappwebview`（WebView2）开隐藏页面，在界面进程里 |
| 本地中继 | Dart 写的 HTTP 服务占 `127.0.0.1:9978`：注入请求头、改写 m3u8、去广告、网盘直链、BT 取流；壳的 `/proxy` 请求转发给对应的 JVM |
| 播放内核 | `fvp`（libmdk，内核闭源）接在官方 `video_player` 上；可弹出独立播放器窗口（`desktop_multi_window`，子窗口里重建一整套状态）；也可交给外部播放器 |
| 其他功能 | 弹幕、外挂字幕、网盘扫码登录、磁力（aria2 子进程）、DLNA、豆瓣元数据、内容过滤、备份、托盘与老板键、检查更新、沉浸模式 |

它的开发记录里有几条对任何 Flutter 桌面项目都成立的经验：

- Flutter 在 Windows 上默认走 Impeller，圆角和渐变多的界面会保留大量整窗大小的离屏缓冲。它实测空载提交内存 600 MB 以上，关掉 Impeller 回退 Skia 后约 140 MB。
- 超长地址（网盘直链 + Cookie）要换成短 token，否则外部播放器报 URL 过长。
- 关窗时先销毁窗口再结束进程，否则 WebView2 和 Flutter 引擎会在退出时崩。

## 2. 两种架构的差别

| | MisaTV：全 Dart + JVM 辅助进程 | 本项目：Kotlin 引擎 + Flutter 界面 |
|---|---|---|
| TVBox 协议逻辑 | Dart 重写一遍 | Kotlin，能直接移植 TVBoxOS / Box 的 Java 实现 |
| jar 蜘蛛 | 跨进程：每次调用是一行 JSON；并发靠多开 JVM；播放地址常指向某一个 JVM 自己的端口，所以要保活进程、上报端口、改写地址 | 同进程：像安卓 TVBox 一样用类加载器加载，蜘蛛实例常驻，只有一个 `/proxy` |
| 由此产生的问题 | 源码里大量"实证"注释都在处理进程边界：结果落在哪个 JVM、端口被残留进程占用、壳的初始化与线程绑定、播放时进程提前退出 | 这一类问题不存在；代价是引擎常驻，jar 与引擎同在一个进程里（见下面的"隔离"） |
| JS 蜘蛛的同步请求 | 每次请求一个 curl 子进程 | QuickJS 通过 JNI 直接调 OkHttp |
| 不用 jar 时的开销 | 没有 JVM；用到才下载、才启动 | JVM 一直在：实测空载工作集约 106 MB |
| 首次使用 jar | 等几分钟下载运行时（约 85 MB） | 包里自带（精简 JRE 约 53 MB），不用等也不依赖镜像站 |
| 安卓 | 跑不了 jar | 同一份引擎代码，用 `DexClassLoader` 原生加载，含加固 jar |
| NAS / 局域网 / iOS | 做不到，逻辑和界面在一个进程里 | 引擎可以单独部署，客户端走同一套协议 |
| 界面与逻辑的耦合 | 嗅探、网盘登录、中继都在界面进程里 | 引擎不依赖界面，可以无界面运行和测试（`--check`） |
| 语言 | Dart 为主，少量 Java shim | Kotlin + Dart 两种，中间隔一层 HTTP 协议 |
| 真实 jar 的兼容性 | **已在大量真实源和加固壳上验证** | **只在演示 jar 上验证过**，真实 jar 的情况要看体检报告 |
| 加固 jar（桌面） | 支持（unidbg 解包 + 影子类） | 不支持 |
| 隔离 | jar 在独立进程里，崩了不影响界面 | jar 崩溃或卡死会影响引擎；需要时可把 jar 运行时挪进子进程，协议不变 |

诚实地说：本项目的架构在纸面上更干净，但 MisaTV 是踩过真实的坑走出来的。它那些针对具体壳的补丁说明，真实 jar 的麻烦远不止"能加载类"。

## 3. 界面方案对比

| 方案 | 适合本项目的地方 | 不适合的地方 |
|---|---|---|
| **Flutter + Kotlin 引擎**（现状） | 一份界面覆盖 Windows / macOS / Linux / Android / iOS；视频是 Flutter 合成器里的一张纹理，弹幕、控制栏、浮层直接叠在上面；`media_kit`（libmpv）和 `fvp`（libmdk）两个成熟内核可选；MisaTV 证明了这条路能做出功能完整的桌面客户端 | 两种语言；桌面细节（多窗口、托盘、安装包）要靠插件拼；Windows 上要手动关 Impeller；内存不如原生 |
| **Compose Multiplatform**（全 Kotlin） | 界面和引擎同语言、可以同进程，省掉本机的 HTTP 层和模型的重复定义；Android TV 上是官方的界面框架；Gradle 插件自带安装包（MSI / DMG） | 桌面端没有官方视频组件。常见做法是嵌重量级的 Swing 组件（界面叠不上去，或要用实验性的混合模式），或者把每一帧拷进 Compose 画布（高分辨率下吃 CPU）——弹幕和浮层正好卡在这里；iOS 上引擎照样不能本地跑；界面要全部重写 |
| **全 Dart + JVM 辅助进程**（MisaTV 的做法） | 不用 jar 时最轻；单一主语言 | 协议逻辑要用 Dart 重写，不能移植安卓实现；jar 跨进程带来的问题见第 2 节；没有可独立部署的引擎 |
| **Electron / Tauri** | 界面开发快 | Win-box 就是 Electron，作者自己放弃了：内存、多窗口、播放器靠 `mpv --wid` 盖在窗口上。Tauri 省内存，但视频要么受限于系统 WebView 的解码能力，要么同样是外挂播放器窗口 |
| **Qt / QML + libmpv** | 桌面播放器的传统强项，视频与界面合成没有问题，内存小 | C++；移动端体验一般；界面开发最慢 |
| **各平台原生界面 + 共享引擎** | 每个平台体验最好 | 界面要写两三遍，一个人维护不动 |

Compose 是唯一值得认真考虑的替代。它的收益（同语言、同进程）落在工程便利上，它的风险（视频与界面叠加）落在这个应用最核心的页面上，所以不换。如果以后重点转向 Android TV，或者 Compose 桌面有了可叠加的硬解视频组件，再评估。

## 4. 当天据此做的改动

| 改动 | 之前 | 之后 |
|---|---|---|
| Windows 客户端关闭 Impeller（`windows/runner/main.cpp`） | 首页空载：工作集 116 MB，提交 466 MB | 工作集 98 MB，提交 242 MB |
| 引擎 JVM 加 `-Xms16m -Xmx1g` 和空闲回收比例 | 工作集 168 MB，提交 598 MB（JVM 默认按物理内存的比例预留堆，这台机器 32 GB） | 工作集 106 MB，提交 93 MB |
| 合计（界面 + 引擎，空载） | 工作集约 284 MB，提交约 1064 MB | 工作集约 204 MB，提交约 335 MB |

测法：打包后的客户端连一个演示引擎，停在首页 45 秒后读进程计数；引擎在访问过三个演示站（采集、JS、jar）、直播列表和一次聚合搜索之后读数。没有测播放中的内存。

对照 MisaTV 自己公布的数字（关 Impeller 后空载约 140 MB，播放且 JVM 在跑时约 240 MB）：本项目空载仍然重一倍左右，一半来自常驻的 JVM，另一半是界面进程本身比它高（242 对 140），原因还没查。

## 5. 接下来从 MisaTV 借鉴什么

GPL-3.0 的代码可以并入 AGPL-3.0 的项目（两个许可证的第 13 条），所以不只是看思路，必要时可以移植，注明来源即可。按价值排序：

1. **加固 jar 的路线**：unidbg 只用来首次解包，之后走纯 Java 的影子类。本项目原计划每次调用都过 unidbg，它的做法更好。
2. **网盘凭据落盘的约定**：jar 蜘蛛不读 `ext` 里的 Cookie，而是读固定位置的文件，它整理出了各蜘蛛家族期望的文件名。
3. **播放器的功能清单**：跳过片头片尾、多音轨、画面比例、缓冲指示、外部播放器、弹幕接口。
4. **界面**：海报流、详情页、沉浸模式的视觉设计。
5. **待查**：界面进程在 Skia 下为什么还比它多 100 MB。

## 6. 什么时候该重新考虑

- 真实 jar 的体检结果很差，而且问题出在"同进程加载"本身（而不是缺桩类）——那就把 jar 运行时挪进子进程，但仍然留在引擎这一侧。
- `media_kit` 停止维护：换 `fvp`，界面代码基本不动。
- 目标变成"只要 Windows，尽快好用"：那应该直接用 MisaTV，或者在它上面改。

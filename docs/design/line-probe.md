# 设计说明：线路体检

> 状态：📋 已排进下一版，还没开始写代码。来由见 [ux-review.md](ux-review.md) 的 1.3；电视上的样子见[原型](prototypes/README.md)里的「线路」和「正在换线路」两块画板。

## 要解决什么

现在是"播了才知道坏"：

- 一条线路最多等 15 秒没有画面才算失败（`player_page.dart` 的 `_startTimeout`），然后换下一条，一条接一条。五条线路都慢，要等一分多钟，期间只有一个转圈。
- 选线路的人看不出哪条好：线路按钮上只有站点起的名字和集数。
- 自动换线路时不知道换到第几条、还剩几条。

目标：**详情页一打开就知道每条线路能不能播、快不快；按下「播放」直接用最好的那条；真要换线路时看得见进度，随时可以自己选。**

## 几种做法

| 做法 | 能发现什么 | 代价 | 结论 |
|---|---|---|---|
| A. 客户端开几个隐藏的播放器各播一条 | 一切，包括解码 | 每条线路一个 libmpv 实例，手机和电视盒子吃不消；流量大 | 不做 |
| B. 引擎解析出地址，取播放列表和第一个分片的开头 | 死链、403 / 404、超时、清晰度、网速 | 每条线路一次解析加几百 KB | **选这个** |
| C. 引擎只解析，不取内容 | 解析失败 | 最省 | 发现不了最常见的情况（解析成功但片源打不开） |

选 B：代理、请求头、`hosts` 规则、解析器都在引擎这边，由它来测和播放时走的是同一条路；测不到的只有"能下载但解不了码"，这种情况少，留给播放器现在的 15 秒兜底。

## 接口

`POST /api/v1/play/probe`，回答是 SSE（和搜索一样的流式结果），每测完一条线路发一个事件。

请求：

```json
{
  "site": "cms",
  "lines": [
    {"line": "线路一", "episodeId": "https://…/1.m3u8"},
    {"line": "线路二", "episodeId": "https://…/a/1.m3u8"}
  ],
  "direct": false
}
```

`lines` 由客户端给：同一集在每条线路上是哪个 `episodeId` 只有它知道（`PlayLine.findEpisode`）。`direct` 和 `/play/resolve` 的含义相同。

事件 `line`：

```json
{
  "line": "线路一",
  "state": "ok",
  "kind": "hls",
  "width": 1920, "height": 1080,
  "resolveMs": 180, "firstByteMs": 420,
  "bytesPerSecond": 3355443,
  "parsedBy": "",
  "reason": ""
}
```

| `state` | 含义 | 客户端怎么说 |
|---|---|---|
| `ok` | 解析成功，播放列表和分片开头都取到了 | 简单：「快」或不标；标准：`1080p · 3.2 MB/s` |
| `slow` | 取到了，但网速低于这个清晰度需要的，或者超过了时间预算才回来 | 「慢」 |
| `dead` | 解析失败，或地址打不开（`reason` 是一句人话：超时、404、被拒绝） | 「打不开」 |
| `sniff` | 要网页嗅探才有地址，体检不替它开浏览器 | 「要试了才知道」 |
| `skipped` | 超过了一次体检的线路数上限，没测 | 不标，可以点「测其余线路」 |

最后一个事件 `end`。连接断开即取消还没测完的。

**预算和限制**（都是引擎的常量，先按这些数写，真实订阅上调）：

- 同时测 3 条；一次请求最多测 6 条，其余回 `skipped`。
- 每条线路：解析最多 6 秒，连接加第一段内容最多 4 秒；读第一个分片的前 512 KB 或 1.5 秒，先到为准。整次请求 10 秒收尾，没回来的标 `slow`（不标 `dead`：慢和坏要分开）。
- m3u8 是主列表（有多个清晰度）时取最高一档的 `RESOLUTION`，再取那一档的第一个分片测速；没有 `RESOLUTION` 就不报宽高。
- 结果按「站点 + 线路 + 集」缓存 5 分钟；同一个主机 2 分钟内两条线路都连不上，这个主机上的其余线路直接标 `dead`，不再去碰。
- jar / js / Python 站点的解析会真的调蜘蛛的 `playerContent`：所以只测当前这一集，不测整部，也不在列表页预测。
- 走和 `/play/resolve` 完全相同的代码（解析器、请求头、`hosts`、「播放」用途的代理），不另写一套。

## 客户端怎么用

1. **详情页**：片子的详情到了就发一次体检（当前要播的那一集）。线路按钮上先是一个小的三色水纹（测速中），结果到一条更新一条。设置里有「打开详情时测线路」开关；手机上默认关，改成按下「播放」时再测（省流量）。
2. **按下「播放」**：
   - 上次看这部片用的线路是 `ok` → 还用它（不打乱习惯）。
   - 否则在 `ok` 的线路里挑：网速够这个清晰度用的（1080p 约 0.6 MB/s，4K 约 2.5 MB/s）里清晰度最高的；都不够就挑最快的。
   - 体检还没回来：照现在的做法从第一条开始，结果到了再决定要不要换。
3. **自动换线路**：跳过 `dead`；体检说 `ok` 的线路给足 15 秒，没测过的给 8 秒。
4. **「正在换线路」卡片**：开播超过 2 秒没有画面，或者发生了一次换线，画面中间不再是转圈，而是一张卡片：每条线路一行（✓ 能播、测速中、✗ 打不开和原因），正在试的那条有水纹；按钮「选一条」（电视上焦点在这）和「停在这里」。出画面后卡片收起，留一句"已换到线路 2，从 42:10 接着播"。
5. **播放信息**（已有的面板）：多一段各线路的体检结果；开发者模式再加毫秒数（解析、首字节）。
6. **遥控和网页控制台**：屏幕状态里的 `player.lines` 带上每条的 `state`，网页的「正在播放」同样显示。

## 不做

- 不测每一集，不测解码，不在后台定时测。
- 不绕过任何东西：打不开就是打不开。
- 不把结果上传到任何地方。

## 怎么验证

- **引擎测试**：演示站里《白昼迷踪 第二季》第一条线路是死链 → `dead` 和原因；演示站加一条限速的线路 → `slow`；主列表取最高一档；事件按完成顺序到；6 条上限；缓存命中不再请求；断开连接后不再请求。
- **客户端测试**：假引擎按给定顺序发事件，线路按钮跟着变；「播放」选中的线路符合上面的规则；卡片上「选一条」「停在这里」的行为；简单模式只出现「快 / 慢 / 打不开」。
- **流程分镜**：从详情页按下播放到出画面的时间，第一条线路是死链时，改之前和改之后各量一次。
- **真实订阅**：采集站、js 站点、jar 站点各一个，看体检结果和实际播放是否一致；记下误判（标 `ok` 却播不了，标 `dead` 却能播）各几次。

## 分几步

1. 引擎接口和测试。
2. 详情页的线路按钮，「播放」按结果选线路。
3. 「正在换线路」卡片，换线时的等待时间。
4. 播放信息里的线路对比；遥控状态里带上结果。

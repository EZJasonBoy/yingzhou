## 怎么管进度

**四份文档，各管一件事，互不重复：**

| 文档 | 回答的问题 | 什么时候改 |
|---|---|---|
| [roadmap.md](roadmap.md)（本文） | 往哪走、先后顺序、为什么 | 规划一个版本时；冒出新想法时（只加一行到「想法池」） |
| [status.md](status.md) | 现在什么是真的：验证过什么、没验证什么、已知缺口 | 每次合并、每次真机验证之后 |
| [CHANGELOG](../CHANGELOG.md) | 每个版本改了什么 | 每次合并 |
| [requirements.md](requirements.md) | 产品是什么、给谁用、守哪些原则；已有功能的清单 | 方向变了时；新功能做完后补进清单 |

**几条规矩：**

1. **新想法不打断当前版本。** 先在本文末尾的「想法池」记一行；规划下一个版本时再挑：要做的升到「下一步」，大的先写一页设计说明（放 `docs/design/<题目>.md`：要解决什么、几种做法、选哪个、怎么验证），其余留在池里。
2. **每个版本一个主题，并且先还债。** 一个版本里至少三分之一是 bug、已知缺口和真机验证，剩下的才是新功能。
3. **同时开的功能线不超过三条**（每条一个分支或一个并行会话），合并一条再开下一条。
4. **"做完"的意思**：有测试；文档跟上（CHANGELOG、status、用到的地方）；在至少一台真实设备上跑过——没跑过的，写进 status.md 的"还没确认的"，不算做完的那一半。
5. **能直接动手的具体事项放 GitHub Issues**：bug、小功能、交互问题、真机验证任务；按版本建 milestone，用标签分领域（引擎、桌面、安卓、电视、iOS、文档）和类型（bug、功能、交互、验证、调研）。路线图只写主题和顺序，需要时链接到 issue。issue 也正好当并行会话的任务说明。

## 一条贯穿的思路：片单和片源分开

好几件看起来不相干的事，其实是同一个结构问题：

- 很多真实配置把**豆瓣推荐站**放在第一个。它只告诉你"有什么好看"，本身没有播放地址；TVBox 的做法是点海报时拿片名去所有站点搜。
- **Kazumi** 也是这样：番剧的目录、简介、放送表来自 Bangumi，规则只负责"这部在哪个站能看"。
- **点播自动换源**：一部片的线路全坏了，要去别的站点找"同一部片"。
- **本地片库**：文件夹里的视频要刮削成"哪部片、第几季第几集"。

所以引擎需要两层：**片单**（看什么：豆瓣、Bangumi、TMDB、本地刮削，带上片名、年份、季集和各家的 ID）和**片源**（在哪看：TVBox 站点、Kazumi 规则、网盘、媒体服务器、以后的插件），中间是**匹配**（同名、同年、同集）。这一层先搭好，后面的换源、Kazumi、片库、插件都站在它上面。

## 下一步

### 1. 用户模式

同一个应用，三种默认值和可见程度，不是三套界面。在「设置 → 外观 → 用法」里换，第一次打开时问一次。下面每一条后面标了第一版做没做。

**用法只改默认值，不拿走能力**（2026-11-22 定，[设计系统「交互」第 1 条](design/system/README.md)）。v0.4.1468 的简单模式是把东西藏掉，结果藏掉的恰好是片源不稳时最需要的（选线路、看为什么卡）。现在的规矩是：每种能力在每种用法里都够得着，用法只决定它摆在第一层还是第二层、默认开还是关、说人话还是给细节。逐项对一遍：

| 能力 | 简单 | 标准 | 开发者 |
|---|---|---|---|
| 继续看 | 首页第一个标签 | 同左 | 同左 |
| 打开时先显示什么 | 继续看 / 站点推荐 | 继续看 / 站点推荐 / 我的 | 同标准 |
| 换站点 | 首页的站点按钮，右边弹出 | 首页顶上的订阅、仓库、站点菜单 | 同标准 |
| 选线路 | 详情页和播放页，叫「线路 1、线路 2」 | 同左，用站点起的名字 | 同标准 |
| 播放信息 | 播放页「信息」，人话 | 同左 | 同左，另有完整统计和链路 |
| 倍速、弹幕、字幕、选集 | 有 | 有 | 有 |
| 我的（历史、收藏） | 在「继续看」里 | 入口 | 入口 |
| 源、网盘 | 在设置里（设置可以上锁） | 入口 | 入口 |
| 分类筛选 | 📋 还没有，要放回来（收起着） | 有 | 有 |
| 下载 | 📋 还没有，要放进详情页的「更多」 | 有 | 有 |
| 刷新详情 | 📋 还没有，同上 | 有 | 有 |
| 诊断与反馈 | 设置 → 关于 | 同左 | 同左，另有「日志」入口 |

**简单模式**：给只想看电视的人（家里长辈、电视盒子）。

v0.4.1468 已有：入口只剩首页、直播、搜索、设置；首页第一个标签是「继续看」（上次那部片 + 一个直接接着播的按钮，下面是最近看过和收藏），站点的推荐和分类保留为后面的标签，站点按钮从右边弹出站点列表（可以往上换仓库和订阅）；线路失败时只说一句人话；播放器保留倍速、弹幕、字幕、选集；设置可以用 4 位密码锁住。之后（v0.4.146825098）：详情页和播放器列出线路，叫「线路 1、线路 2」；播放页有「播放信息」。还没有：直接打开上次的直播频道、换源失败时的人话、更大的字和按钮、忘记密码的找回办法，以及上表里标 📋 的几项。原型见 [design/prototypes](design/prototypes/README.md)。
- 首页只有「继续看」和一个站点（或直接打开上次的直播频道，像开电视一样）；没有"源、引擎、局域网、网盘"这些概念，设置收进带密码的入口。
- 自动换线、自动换源一律打开；出错时说人话（"这个频道暂时看不了，已换到下一条"），不出现错误码和网址。
- 大字、大按钮；遥控器和触屏都只留最常用的操作。

**标准模式**：现在的样子。

**开发者模式**：给自己调兼容、给愿意帮忙排查的用户。

v0.4.1468 已有：播放统计浮层（I 键；编码、分辨率、帧率、硬解、输出、掉帧、音频、音画同步、码率、缓冲和网速，没有色彩与 HDR）；链路面板（订阅、站点、失败的线路、解析方式和耗时、播放地址和请求头、首帧耗时，可以复制脱敏后的诊断信息）；「日志」页（客户端这一侧的每一步，电脑上另有内置引擎的输出）；详情页的站点 key、`vod_id` 和首集地址。还没有：引擎侧的日志接口和蜘蛛的 `console.log`（现在的日志只是客户端看到的）、复制为 curl / mpv 命令、外部播放器、单站体检、缓存命中。
- **播放统计浮层**（参考 mpv 的 stats、MPC-BE 的统计信息、YouTube 的"详细统计信息"）：解码器和是否硬解（`hwdec-current`）、编码格式、分辨率、帧率（片源 / 实际 / 屏幕）、掉帧（解码 / 显示）、码率、缓冲时长和网速、音画同步、色彩与 HDR 信息、渲染方式。
- **链路追踪**：这一集从蜘蛛 `playerContent` 拿到什么、经过哪个解析器、是否嗅探、最后交给播放器的地址和请求头（UA、Referer）、每一步耗时；经引擎还是直连、播放缓存命中多少。可以"复制为 curl"、"复制为 mpv 命令"、"用外部播放器打开"（mpv、PotPlayer、VLC、IINA）。
- **引擎侧**：引擎日志实时滚动、JS 蜘蛛的 `console.log`、单个站点"重新加载蜘蛛"和"只体检这一个站点"、查看站点的原始配置。
- 截图和复制时照样遮掉订阅地址、令牌和签名参数。

### 2. 片单层与自动换源

即上文"片单和片源分开"：媒体身份（片名、年份、季集、豆瓣 / TMDB / Bangumi ID）、匹配、跨站点搜索同一部片；在它上面做**点播自动换源**（线路全坏时带着进度换到别的站点的同一集）和豆瓣 / Bangumi 推荐页。

v0.4.1421 已经先做了只靠片名的一版：推荐站（`msearch:` / 空 id）按片名找、自动打开第一个同名结果，详情没线路、打不开、线路全坏时也换站（`changeable`、规整后的片名完全相同、年份差一年以内），详情页可以「换一个」。片单层要补上的是更可靠的匹配（季、集、年份、各家 ID）和不依赖站点搜索的推荐页。

### 3. 播放器

参考 mpv、MPC-BE、PotPlayer、VLC、IINA、Infuse、Kodi 和各家 B 站客户端，按"用得多、做得动"排：

| 类别 | 功能 |
|---|---|
| 进度 | 拖动时的缩略图预览（mpv 的 thumbfast 思路）；章节；跳过片头片尾（TVBox 有）；A-B 循环；逐帧 |
| 画面 | 比例、裁切、缩放、旋转、镜像；亮度、对比度、饱和度、伽马；截图（带 / 不带字幕）；截一段动图 |
| 声音 | 音画同步和字幕偏移微调；音量标准化（`loudnorm` / `dynaudnorm`）；夜间模式（压缩动态范围） |
| 其他 | 睡眠定时；外部播放器打开；投屏：发到电视（DLNA / AirPlay），以及把映舟当成接收端 |
| 画质增强 🔬 | 着色器预设：Anime4K、FSRCNNX、ArtCNN、RAVU、NNEDI3、KrigBilateral（色度）、adaptive-sharpen、去色带；HDR 色调映射（`gpu-next`）；补帧：mpv 自带的 `interpolation` 先上，VapourSynth（MVTools、RIFE）再评估 |

画质增强要先查两件事：media_kit 的视频输出走 libmpv 的渲染接口，`glsl-shaders` 在这条路径上是否都生效、性能如何；media_kit 自带的 libmpv 是否编进了 VapourSynth（大概率没有，那就要自己编 libmpv 或只在桌面上可选）。着色器文件的许可证逐个核对后再打包。

### 4. 字幕与弹幕

- **弹幕源**：弹弹play 开放接口（按片名和集数匹配，Kazumi 也用它，要申请 AppId）、B 站弹幕（按视频的 cid）、现有的自定义接口。匹配交给片单层。
- **弹幕体验**：弹幕密度曲线画在进度条上（"高能进度条"）；屏蔽词、合并重复；B 站内容可用 B 站提供的人像蒙版防挡。
- **字幕搜索**：按文件名和片名搜在线字幕（OpenSubtitles 等，要各自的接口密钥），自动匹配本地同名字幕。
- **AI 字幕** 🔬：本机 whisper.cpp 转写（显卡加速可选）；引擎的播放缓存里本来就有比播放进度靠前的分片，可以先一步转写，播到时字幕已经有了；翻译用本机模型或用户自己填的大模型接口。**默认关闭，默认在本机算**，要把音频发给第三方时必须用户自己选。

### 5. 引擎插件：从兼容 TVBox 到「映舟源协议」

TVBox 的站点只有"首页、分类、详情、播放"四个动作，表达不了账号登录、个人动态、评论、音视频分离的 DASH、自带弹幕。B 站这类来源需要更多。打算把引擎对来源的要求整理成一份**按能力声明、带版本号的源协议**，TVBox 站点只是其中一种来源。

**能力**（插件声明自己支持哪些）：片单（首页、分类、筛选）、搜索、详情、播放地址、直播与节目单、弹幕、字幕、账号（扫码 / Cookie 登录）、个人动态、同步（历史、收藏、追番）、操作（点赞、收藏等）。

**三种写法：**

| 写法 | 适合 | 参照 |
|---|---|---|
| 声明式规则（JSON，XPath / CSS 选择器） | 结构简单的网页站，写起来最快，也最安全 | Kazumi 规则、drpy 规则 |
| 脚本（JS 模块，在 QuickJS 沙箱里跑） | 要加解密、签名、多步请求的来源 | TVBox 的 JS 蜘蛛、IINA 的插件 |
| 远程（HTTP 接口：一个清单加几条固定的路由） | 任何语言实现、可以部署在别处 | Stremio 的 addon 协议（catalog / meta / stream / subtitles） |

**清单**写明 id、名字、版本、协议版本（像 Kazumi 的 API Level 那样逐级加功能）、能力、要访问的域名、设置项。**安全**：只能访问声明的域名；每个插件独立存储；账号凭据存在系统的钥匙串里，只发给对应的网站；插件来源和更新走索引文件（像 KazumiRules 的 `index.json`），可以有不同的信任级别。

**适配器**：现在的 TVBox 兼容层变成"TVBox 适配器"；第二个是 Kazumi；Stremio addon 可以评估。

**Kazumi 规则**（先做，它也是检验协议的第一块）：规则是一个 JSON：`api`（协议级别）、`name`、`version`、`baseURL`、`searchURL`（`@keyword` 占位，可用 POST）、`searchList` / `searchName` / `searchResult`（XPath）、`chapterRoads` / `chapterResult`（XPath）、`useWebview`、`useNativePlayer`、`userAgent`、`referer`、`adBlocker`。引擎要补的只有 XPath（JVM 上 jsoup 有 `selectXpath`）；播放页嗅探和 HLS 去广告都已经有。目录从 Bangumi 来、弹幕从弹弹play 来，正好落在片单层和弹幕源上。规则仓库是 MIT。

**B 站**（之后，作为可选安装的插件，不默认内置）：扫码登录和多账号、推荐 / 热门 / 动态 / 历史 / 收藏 / 追番、番剧、DASH 播放（音视频分开，交给 mpv 的外挂音轨或 EDL）、protobuf 分段弹幕、AI 字幕、把映舟当投屏接收端（DanmuTV 实现了官方 App 用的 UPnP 和 NVA 协议）。参考 PiliPlus（Flutter，同样用 media_kit）、wiliwili（C++ / mpv，GPL-3.0）、DanmuTV（tvOS，GPL-3.0）、BBLL（安卓电视，不开源），接口资料看 bilibili-API-collect（CC BY-NC，只作参考）。GPL-3.0 的代码可以带着署名移进本项目（AGPL-3.0）。风险要写在插件说明里：接口不是官方公开的，随时会变；第三方客户端可能触发风控；不绕过任何会员、地区和版权限制。

### 6. 本地片库与媒体服务器

在片单层之上：扫描本机文件夹和网盘 → 从文件名认出片名和季集 → 刮削（有 NFO 先用 NFO，再查 TMDB、豆瓣、Bangumi）→ 海报墙、按季分集、看到哪、合集，局域网里的设备共享同一个片库。另外把 **Jellyfin / Emby / Plex** 接成来源：它们本来就有片库和刮削，接进来就能用。

## iOS

客户端是 Flutter，本来就能编到 iOS；难的是引擎。引擎跑在 JVM 上，iOS 不允许 JIT，也没法跑 JVM 和安卓的 dex。

| 做法 | 能做到 | 代价 |
|---|---|---|
| **A. 纯客户端，连别处的引擎** | 全部功能，jar 蜘蛛也行 | 家里要有一台常开的电脑、NAS 或电视盒子；在外面要经 Tailscale 之类。配对、远处直连片源都已经有了 |
| **B. 本机轻引擎（Kotlin Multiplatform）** | 采集站、JS 蜘蛛、直播与节目单、解析、嗅探（WKWebView）、去广告、播放缓存；Python 蜘蛛可选 | 把引擎核心从 JVM 专属代码迁到跨平台代码，见下 |
| **C. 本机跑 jar（解释执行的 JVM）** | jar 蜘蛛 | 要一个能在 iOS 上纯解释执行的 JVM，加上安卓桩类和 dex 转换；速度和兼容性都没有把握，只值得做一次小实验 |
| **D. B + 按站点自动转给 A** | 能本机跑的本机跑，jar 站点自动交给配对的引擎 | B 的代价，加一点路由 |

**建议走 D，分三步：**

1. 📋 先出 A：iOS 客户端连局域网或 NAS 上的引擎。代码改动小，马上有用。
2. 🔬 B 的可行性实验：把一小片（配置解析、采集站、m3u8 去广告）挪到 `commonMain`，在 iOS 模拟器上跑通。
3. 根据实验结果决定是否整体迁移；迁完再加"按站点转发"。

**B 有多大**：引擎核心 `engine/core` 约 60 个文件、9400 行，大约三分之一的文件碰到 JVM 专属的 API（OkHttp 12 个文件、`java.io` 19 个、`java.util.concurrent` 11 个等）；JS 运行时还用了 jsoup 和 Gson。对应的跨平台替代都有：Ktor client（iOS 上用 Darwin 引擎）、kotlinx-io、kotlinx-coroutines、kotlinx-serialization、Ksoup（jsoup 的跨平台移植）；quickjs-kt 本身就有 iOS 版本；Ktor 的服务端在 Kotlin/Native 上只支持 CIO、不支持 TLS，监听 `127.0.0.1` 够用。迁移的好处不止 iOS：同一份引擎代码以后也能用在 tvOS。

**Python**：CPython 从 3.13 起官方支持 iOS，可以嵌进应用，但安装包会大不少。

**分发是绕不开的前提**：App Store 不允许下载执行会改变应用功能的代码，影视聚合类应用也很难过审。现实的渠道是自己用 Xcode 编译安装（DanmuTV 就是这样）、AltStore / SideStore 一类侧载、欧盟的第三方应用市场。投入多少，要看打算走哪条渠道。
